# Wallet Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Wallet personal app with an always-visible credit balance, welcome credits on onboarding and referral credits for both parties when an e-mailed friend is onboarded, kept as an append-only ledger.

**Architecture:** All data in MainDB (new script 27): `dbo.WalletLedger`, `dbo.Referrals`, three `PlatformSettings` keys, and a trigger on `dbo.Users` that runs one idempotent onboarding procedure. A new `WalletService` + `WalletController` in the API; an Angular `WalletService` signal feeds a balance chip in both headers and the new `apps/wallet` page.

**Tech Stack:** SQL Server (T-SQL scripts run by hand in SSMS), ASP.NET Core + ADO.NET via `BaseRepository`/`MainDbHelper`, xUnit (`EncryptzTests`), Angular 21 standalone + signals, Vitest (`ng test`).

**Spec:** `docs/superpowers/specs/2026-10-29-wallet-design.md`

## Global Constraints

- Every SQL change is a **new numbered file**; never edit an existing SQL file. This one is `EncryptzAPI/Database/MainDB/27_Wallet.sql`, SAFE TO RE-RUN, header + guard style of `26_Platform_Database_State.sql`.
- **Never run SQL against the server in `appsettings.json` — it is LIVE.** Tests read the script text only; the user runs the script.
- Do not modify `EncryptzAPI/appsettings.json` (it has the user's own uncommitted change).
- Credits are INT. Settings `WelcomeCredits`, `ReferralCredits`: 0 – 100000, seeded `0`, 0 = reward off (no ledger row).
- `WalletStartedAt`: written once by script 27 (`CONVERT(varchar(19), GETDATE(), 126)`), never overwritten, not editable (no `settingHelp` entry, and `PlatformSettingRules.Validate` refuses it).
- Welcome only for users with `Users.CreatedAt >= WalletStartedAt`. Onboarded = `LTRIM(RTRIM(FullName)) <> ''` AND `LTRIM(RTRIM(ISNULL(MobileNumber,''))) <> ''`, in `dbo.fn_Wallet_IsOnboarded` only.
- Ledger `Kind` values exactly: `Welcome`, `ReferralJoined`, `ReferralInviter`. Referral `Status` exactly: `Sent`, `Joined`, `Credited`.
- Invite limit: 20 per inviter per calendar day (`WalletRules.MaxInvitesPerDay = 20`).
- Ledger notes: Welcome → `Welcome to Encryptz`; friend → `Joined with an invite from {inviter FullName}`; inviter → `Your friend {friend FullName} joined`.
- User-facing refusals: own e-mail → `You cannot invite yourself`; existing account → `This person already has an account`; limit → `You can send up to 20 invites a day`; bad e-mail → `Enter a valid e-mail address`.
- Sign-up link: `{App:PublicUrl}/register?ref={token}&email={url-encoded e-mail}`; `App:PublicUrl` read from configuration with fallback `https://serviceapp.encryptz.in`.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Trigger must never break a user save:** a user insert/update with settings at 0, no referral, or a pre-launch user must succeed and write nothing. Pinned in Task 1 (script asserts the procedure returns early on each, and the trigger has no RAISERROR/ROLLBACK).
2. **Double payment:** the profile saved twice, or the trigger fired by an unrelated column update (e.g. password change), must not pay again. Pinned in Task 1 (unique filtered indexes + NOT EXISTS under UPDLOCK asserted).
3. **E-mail case/space differences:** `Anu@X.com ` invited and `anu@x.com` registering must link. Pinned in Task 1 (`LOWER(LTRIM(RTRIM(...)))` on both sides) and Task 2 (`WalletRules.NormalizeEmail`).
4. **Referral token from another inviter's link vs. a different e-mail:** the token wins; a garbage/unknown token falls back to e-mail matching without failing registration. Pinned in Task 1 and Task 3 (`TRY_CONVERT(uniqueidentifier, …)`; a bad token is passed as NULL).
5. **Invite mail fails (SMTP down):** the invite is still saved and the API returns success with `mailSent = false`. Pinned in Task 3.

  - `dbo.sp_User_SelfRegister` = the script 06 version plus `@ReferralToken UNIQUEIDENTIFIER = NULL`; just before the INSERT: `EXEC sp_set_session_context N'ReferralToken', @ReferralToken;` and after it reset to NULL. Same result set as before.
  - `dbo.sp_Wallet_GetBalance @UserId` → `Balance INT` (ISNULL SUM).
  - `dbo.sp_Wallet_GetLedger @UserId, @Page, @PageSize` → `EntryId, Amount, Kind, Note, CreatedAt, TotalCount`, newest first.
  - `dbo.sp_Wallet_GetReferrals @UserId` → `ReferralId, Email, Status, SentAt, JoinedAt, CreditedAt, FriendName`, newest first.
  - `dbo.sp_Wallet_SaveReferral @InviterUserId, @Email` → one row `Result VARCHAR(20)` (`Created`, `Resent`, `Self`, `HasAccount`, `Limit`) + `Token UNIQUEIDENTIFIER NULL` + `InviterName NVARCHAR(200)`. Order of checks: own e-mail → `Self`; e-mail in `dbo.Users` → `HasAccount`; 20 or more of the inviter's referrals with `SentAt` today → `Limit`; existing row for (inviter, e-mail) → update `SentAt`, `Resent`; else insert, `Created`. A resend counts toward the daily limit.

`sp_Wallet_OnUserOnboarded` order (one transaction):
1. return unless `fn_Wallet_IsOnboarded = 1` and the user's `CreatedAt >= TRY_CONVERT(datetime, WalletStartedAt)` (missing/unparsable start → return).
2. if no referral has `FriendUserId = @UserId`: pick `Referrals` by `Token = TRY_CONVERT(uniqueidentifier, SESSION_CONTEXT(N'ReferralToken'))` with `Status='Sent'` and `InviterUserId <> @UserId`, else earliest `Sent` by normalized e-mail; set `Joined`, FriendUserId, JoinedAt.
3. welcome: if `WelcomeCredits > 0` and NOT EXISTS (WITH (UPDLOCK, HOLDLOCK)) Welcome row → insert.
4. referral `Joined` for this friend: if `ReferralCredits > 0` insert `ReferralJoined` (friend) and `ReferralInviter` (inviter) rows; set `Credited` + CreditedAt either way.
